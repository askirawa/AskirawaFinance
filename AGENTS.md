# Askirawa Finance — Agent Notes

> Built with Arc Studio - money-powered apps in minutes

## What This App Does

Askirawa Finance is a programmable USDC treasury for companies on Arc. Journey: Connect Company Wallet, create payroll or a recurring payment, request approval, approvers approve on-chain, execute, track. Every balance, request, approval, schedule and payment shown comes from the Treasury v2 contracts. Browser storage holds only display-name labels, unsent form drafts and pending transaction hashes.

## Network

- Treasury v2 target: Arc Testnet (chain ID 5042002), USDC `0x3600000000000000000000000000000000000000` (6 decimals, verified read-only). Test funds only.
- Automation Registry reads: Arc Mainnet (chain ID 5042). No treasury is deployed on mainnet and none should be until an independent audit is done.
- Explorers: https://explorer.testnet.arc.io (testnet), https://explorer.arc.io (mainnet)

## Treasury v2 migration notes

- Frontend (current): `src/chain/*` is the layer the shell pages use (config, ABI generated by `scripts/gen-chain-abi.ts` from `contracts/out`, reads, writes, history, pending-transaction tracking). Pages: Dashboard, Payroll, Recurring Payments, Approvals, Team, Activity, Settings, Governance (older v2 page using `src/lib/v2`, `src/hooks/v2`, `src/components/v2`), Escrow and Vesting (Coming Soon only), and a read-only legacy Automation Registry viewer reached from Settings. Analytics, Audit Log, Notifications, Transactions and Organization are no longer routed (browser-local, kept in the repo unused), as are the v1 hooks and components.
- Only payroll requests end in a payment. A confirmed schedule request means the schedule is registered, not that anyone was paid; the UI words it that way. Paused schedules restart only through an approved request.
- The default chain is Arc Testnet (5042002). Arc Mainnet is used only when `VITE_CHAIN_ID=5042` is set explicitly. The app never switches the wallet's network by itself.
- A write is shown as successful only after a mined receipt with status success; module `execute` additionally checks the logs, because the module records a failed payment as a soft failure instead of reverting.
- Keeper: `server/keeper-core.ts` (tested) and `server/keeper.ts`. Refuses mainnet unless `KEEPER_ALLOW_MAINNET=yes`.
- Deploy policy (script only, the core contract is unchanged): 3+ approvers, quorum <= approvers - 1, min config delay >= 1h, payroll delay >= 5m, separate guardian or `GUARDIAN_DISABLED=yes`.
- Recovery (option B-c on B-a) is implemented as a separate immutable contract `contracts/v2/TreasuryRecovery.sol` (a single contract would exceed the 24,576 byte limit). The treasury exposes one hook, `installRecovery`, callable only by its immutable `recovery` address. Config: council 3, threshold 2, 30 day inactivity, 14 day timelock with approver-quorum veto, 7 day cooling. Not independently audited. Design, limits and residual risks: `docs/recovery-design.md`. Deploy order: recovery, treasury (binds it), module.

## Status (what is verified and what is not)

Verified locally on a throwaway anvil chain with test accounts, driven through a real browser with a mock wallet (no live network transaction was sent):
- Payroll request with a dry run, two approvals, safety wait, execution, recipient and treasury balances, receipt link
- Rejected request, wallet rejection, mined-but-reverted transaction, insufficient treasury balance message
- Recurring payment: request, approval, registration (no payment), due payment run, pause, restart request and approval, cancel
- Add funds (allowance then deposit), pending transaction surviving a reload, wrong-network banner with explicit switch
- Backend sign-in: nonce binding, replay, CORS allow-list, signed cookie, rate limit (`server/siwe.test.ts` plus a live run)

Not done or not verified:
- Treasury v2 is NOT deployed anywhere. No independent audit. Lost approver keys: see `docs/recovery-design.md`.
- Nothing runs the keeper in production yet. A registered schedule pays only when someone triggers the due payment (the app's Run due payment button, or the keeper in `server/keeper.ts`).
- Escrow and Vesting: no contracts, no UI beyond Coming Soon.
- Team roles Owner / Finance Manager / Viewer are labels only; the contract knows approvers, proposers and one guardian.
- The backend (`server/index.ts`) is not called by the app. Its roles are off-chain labels and grant nothing on-chain.
- Browser clock vs chain clock: countdown text uses the browser clock, "Due now" uses the chain.

- `contracts/v2/` : AskirawaTreasury, RecurringPaymentModule, TreasuryRecovery, ScheduleMath. `contracts/test/v2/` : Foundry tests
- `contracts/script/DeployTreasuryV2.s.sol` : testnet-only deployment script with address and policy validation
- `contracts/TreasuryV2-*.md`, `docs/recovery-design.md` : design documents
- `src/chain/` : on-chain reads, writes, history, pending transactions. `src/pages/`, `src/components/{flow,approvals,payroll,recurring,dashboard,activity,team,pagekit}/` : UI
- `server/keeper.ts`, `server/keeper-core.ts` : recurring payment keeper (tested). `server/index.ts`, `server/siwe.ts`, `server/db.ts` : optional sign-in and organization-label backend

## What Requires External Setup

1. Deploy to Arc Testnet following `docs/testnet-deployment-checklist.md` (needs your approver, council and guardian addresses), then set the VITE_ variables and restart the dev server.
2. Run the keeper on a persistent host with a dedicated gas-only wallet (`docs/keeper-setup.md`).
3. Decide and complete an independent audit before any mainnet use.
